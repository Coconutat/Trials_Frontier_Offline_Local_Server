# 午夜杯与碉堡运营手册

> 本手册描述本地服务器当前实现，不代表官方服务器或官方原版规则。建议先在临时数据目录验证，再修改正式运行数据；所有操作都应记录操作者、时间、profile 和撤销编号。

## 0. 开始前

1. 启动本地服务器后，在同一局域网内打开管理页面；不要把管理端口暴露到公网。
2. 先备份 `server/data` 中将要修改的配置、账号存档和 `pvp_state.json`。不要直接编辑运行中的 JSON；优先使用后台页面的保存操作。
3. 后台改动通常由 `/__api/admin/weekly`、`/__api/admin/bunker` 等接口写入，并由审计/撤销入口保留记录。保存后先用 GET 检查返回值，再让玩家重新进入对应模式。
4. “服务器返回成功”只证明 HTTP/服务端状态链通过；客户端本地地图列表、横幅缓存和真机刷新没有证据时必须按“需实测”处理。

## 1. 午夜杯（Weekly）

### 1.1 这是什么

午夜杯是“一届一周、一条赛道”的 weekly 活动。服务端核心配置位于 `server/tf_server.py:303-340`，当前默认 `window_days=7`、`track_id` 为当前赛道、`leaderboard_id=0` 表示按本周赛道推导榜单。`week_offset` 用于模拟翻周；不要把它当成永久历史赛季。

一届使用一台车：`bike_id=0` 时按赛道级别自动选择且整周固定；显式 `bike_id` 必须与赛道级别兼容。`loan_upgrade` 是租借车的升级级数，不是把车永久写进玩家车库（同一段源码的注释明确说明租借车不会进入车库）。

### 1.2 开始前检查

按以下顺序操作：

1. 在后台确认 `track_id` 是有效赛道目录中的整数，并确认该赛道有可读取的 ghost/榜单数据。当前赛道选择与 PVP 对局赛道选择不是同一个接口。
2. 确认 `leaderboard_id`：`0` 使用当前周推导值；显式值只在你有对应榜单数据时使用。
3. 检查 `left_retry_times`（默认 3）与 `cooldown_seconds`（默认 3600）。次数用完后的冷却由服务端配置决定。
4. 检查 `fake_field`、`fake_field_base_ms`、`fake_field_fast_pct`、`fake_field_slow_pct`。`fake_field=0` 表示关闭合成对手。
5. 检查 `reward_slots` 和 `reward_ids`。`reward_slots` 是每档发几件；客户端在奖励池中选择，不能把它当成金额或总奖品数。
6. 保存后让玩家退出午夜杯并重新进入，再检查客户端显示；这一步当前没有完整真机契约证明，必须记录为实测结果。

### 1.3 奖励怎么分配

`reward_ids` 为空时使用服务端内置的档位到奖励池映射；非空时按档位覆盖。例如：

```json
{"platinum": [3, 8, 13]}
```

表示把最高档改为指定的奖励池。先确认客户端能识别池子编号，再保存；不要把物品栏 `item_id` 直接当作奖励池编号。

新手例子：想把最高档从默认池换成三个已知奖励池，先备份配置，填 `reward_ids`，设置 `reward_slots=1`，保存，再用测试账号完成一轮并核对奖励日志。若 HTTP 成功但客户端没有奖励，先检查玩家是否仍在旧周窗口，再撤销该审计记录，不要重复发奖。

### 1.4 开始、结束与翻周

- 开始：设置本届 `track_id`、榜单、车辆、租借升级和奖励后保存；用一个测试账号请求 weekly 配置并检查响应。
- 正常结束：按 `window_days` 等待窗口结束，或按现有 weekly 管理入口结束本届；先保留审计记录和玩家结果。
- 提前结束/翻周：只在测试环境使用 `week_offset`；它会模拟服务器进入下一周，不是删除旧玩家数据。改回原值后重新读取配置。
- 非默认 `window_days`：源码明确标注为实验性，未完成真机验证，不应对玩家承诺与官方行为一致。

### 1.5 常见故障

| 看到什么 | 检查什么 | 恢复方式 |
|---|---|---|
| 进入后没有赛道 | `track_id`、榜单 ID、配置 JSON 是否可读 | 恢复最近备份，选择目录中存在且有数据的赛道 |
| 对手出现但 replay 下载失败 | ghost 文件、track ID、content ID、榜单行是否同一赛道 | 不伪造 200 或 replay=0；恢复可读 ghost，并重跑本地链路 |
| 次数变为 0 | `left_retry_times`、冷却时间和账号窗口 | 等待冷却或在测试环境恢复配置；不要直接改玩家结果 |
| 奖励重复/不符合档位 | `reward_slots`、`reward_ids`、客户端奖励池和审计记录 | 停止继续发奖，先撤销错误配置/记录，再用测试账号验证 |
| 服务端已返回新配置但手机未变 | 客户端是否退出并重进、是否缓存旧周时间戳 | 标记为客户端未证实，收集请求/日志后再处理 |

## 2. 碉堡（Bunker / PVP）

### 2.1 赛季与窗口

核心配置在 `server/tf_server.py:166-266`：

- `duration_days` 是赛季窗口长度，当前默认 30 天。
- `advance` 推进自动派生的内部赛季窗口；`display_offset` 只改发给客户端的显示编号，不改变内部窗口或玩家档案。
- 显式历史赛季查询必须使用该赛季自己的窗口，不能把 `display_offset` 当作时间迁移。

保存赛季配置后，先 GET 检查 `start/end` 和显示编号，再让测试账号重新初始化 PVP。玩家结束赛季时，服务端会按窗口变化结算并复位段位；任何提前推进都应在测试环境完成。

### 2.2 赛道、车辆与 AI

`server/tf_server.py:4722-4762` 的 `_pvp_tracks` 说明：一局最多 3 条赛道；若 `track_ids` 为空，就从 `candidate_tracks` 随机抽取最多 3 条；若启用按车随机，服务端会按赛道级别和玩家拥有的车过滤，没有对应车的赛道会被换掉；没有可用候选时使用兜底赛道，并补足到 3 个槽位。

车辆级别判断在 `server/tf_server.py:4647-4671`：车辆 tier 等于赛道 tier、车辆 tier 为 255，或赛道级别未知/255 时可用。新手不要随意填写固定赛道与固定车辆；先从目录和玩家车表确认兼容性。AI 对手和 bot 成绩属于服务端对局逻辑，不能用预填 ghost 冒充真人成绩。

### 2.3 奖励与筹码

筹码曲线由 `chip_equation_x` 和 `chip_equation_y` 控制，源码 `server/tf_server.py:202-212` 明确说明二者不能同时为 0；修改前先保存旧值并用测试账号核对增长速度。

赛季奖励在 `server/tf_server.py:213-266` 的扁平 `rewards` 表中：

- `rank` 是档位；当前实现需要覆盖 0–25 的档位，缺档等于该档没有奖励。
- `item_id=1` 是金币，`item_id=2` 是钻石。
- `item_id=145` 的 `amount` 是 RewardID，不是物品数量。
- 每档数额是增量，客户端会累加已达成档位；填写 1000 表示该档增量 1000，不是把库存总额设为 1000。
- 同一档特殊奖励不要重复填写，否则可能重复发放。

新手例子：若要给 rank 10 增加 200 金币，应修改该档 `{rank:10,item_id:1,amount:200}`，而不是把 amount 填成玩家最终应有的金币总额；若需要特殊季奖，先确认 RewardID，再只保留该档一条 `item_id=145` 记录。

### 2.4 操作流程

1. 备份 `pvp` 配置和 `pvp_state.json`。
2. 设置赛季窗口、`advance/display_offset`、星级数组、筹码曲线和奖励表；逐项保存，不要一次混入未知字段。
3. 在 `track_ids` 为空时先用候选池测试随机/车辆过滤；固定赛道只在已有对应 ghost、目录和车辆条件时使用。
4. 用测试账号调用 PVP 初始化，检查最多 3 个赛道、车辆和响应字段；再开始一局，核对开始/结束、胜负和筹码变化。
5. 赛季结束后用同一账号检查 rank、奖励增量和审计记录；出错先停止继续结算，再用后台撤销恢复。

## 3. 统一排障与撤销

1. 记录 profile、配置版本、操作时间和响应；不要在报告中粘贴密码、token、设备标识。
2. 先 GET 当前状态，再查服务器日志和审计记录；不要通过重复 POST 试错。
3. 发现错误时使用后台撤销入口恢复上一条记录；若涉及赛季/周窗口，恢复配置后重新初始化测试账号。
4. 用临时账号做最小复现，再运行现有回归；不要直接改 `server/data` 中的玩家实时数据。
5. 验收必须分层记录：函数/API 回归、回环 HTTP、真机客户端。前一层通过不代表后一层通过。
